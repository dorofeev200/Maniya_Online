# BALANCER-LAUNCH-GAP-001 — почему запуск видео медленный на контентных фильмах

Дата: 2026-08-19. Статус: **READ-ONLY исследование** (код/тесты/commit/push/deploy НЕ менялись).

Метод: трассировка launch-flow по коду (`index.js` → `store.js` → `SkazProvider` → `SkazClient` →
`availability.js`) + факты из `balancer-final-availability-001-report.md`. Замеры ниже — **code-derived
детерминированные границы** (таймауты/дедлайны/волны), не live-прогон (probe-скрипты прошлой волны удалены,
аккаунт-пара замаскирована).

---

## 1. Launch-flow (что на самом деле происходит при запуске)

```
/sources/card  → defaultChecker.card() → computeCard()
                  └ primary: Promise.allSettled(все sources), deadline=12с
                  └ confirm:  strictConfirmAllHosts/confirmWithBackoff, confirmDeadline=32с
/sources        → статический реестр (show из provider.show, БЕЗ похода в кластер)
/videos?provider → getVideosForRequest → provider.videos(withPinnedHost(...))
                    └ withPinnedHost = defaultChecker.pinnedHost(providerId, userUid) — ДЕШЁВОЕ чтение Map
                    └ SkazProvider.movieVideos → collectMovieCards → client.getLite → _scanLite(6 хостов)
/video?provider  → getVideoForRequest → provider.resolveVideo(withPinnedHost(...))
                    └ _cachedCollectMovieCards (nav-cache 5 мин) / resolveCardItem → resolveVideoJson/resolveStream
```

**Ключевой факт №1:** availability-скан (`computeCard`) живёт ТОЛЬКО в `/sources/card`. `/videos` и `/video`
**НЕ перезапускают availability** — они читают только пин (`pinnedHost`, Map-lookup O(1)). «Повторной
availability-проверки уже после выбора источника» в коде **НЕТ** (проверено по `index.js:252-274` +
`store.js:103-223`).

---

## 2. Где реально возникает задержка

Задержка запуска состоит из двух независимых частей:

| фаза | что | стоимость | источник |
|---|---|---|---|
| A. Карточка | `/sources/card` availability | primary ≤12с + confirm ≤32с | наш код |
| B. Плейбек | `/videos` `_scanLite` + `/video` `resolveVideoJson` | 1..6 хостов × ≤15с таймаут (стоп на первом usable) | **наш + upstream** |

Одиссея останавливается на фазе A (всё HIDE → плейбека нет → «задержки запуска» не видно).
Контентные фильмы проходят и A, и B — поэтому «заметная задержка при запуске видео» наблюдается только на них.

---

## 3. Почему фаза B медленная на контентных фильмах — root cause

Фаза B должна быть быстрой за счёт пина (`pinnedHost` → `_scanLite` стартует с ноды, где availability
авторитетно нашла контент). Пин ускоряет `/videos` с «полный скан 6 хостов» до «1 запрос на правильную ноду».

Пин ломается в трёх местах (все — наша логика, не upstream):

1. **Пин живёт 60с, когда на фильме скрыт хотя бы один источник.**
   `availability.js:1214` → `pinTtl = hasConfirmedHide ? HIDE_TTL_MS : ttlMs` (`HIDE_TTL_MS = 60с`).
   Почти любой фильм скрывает ≥1 источник (503/пустой), поэтому пин для **рабочего** источника
   укорачивается до 60с из-за **чужого** скрытого источника. Между открытием карточки и кликом по
   источнику (>60с) пин истекает → `/videos` делает полный последовательный скан 6 хостов.

2. **Пин пишется ТОЛЬКО на cache-miss.**
   `card()` на cache-hit (`availability.js:1002-1010`) возвращается раньше, **не переписывая пин**.
   Повторное открытие карточки из кэша (0 мс) оставляет `/videos` БЕЗ пина → снова полный скан.

3. **Confirm-фаза гоняет все eligible-сканеры параллельно без глобального maxInFlight.**
   `computeCard` → `Promise.allSettled(eligible.map(...))` (`availability.js:1134`): каждый
   `strictConfirmAllHosts` сам по себе WAVE=2, но 5–8 источников × 2 = 10–16 одновременных запросов
   в кластер → снова триггерится троттл (порог >2 на аккаунт, зафиксирован в `final-availability-001 §A.3`).
   Итог: таймауты на части хостов → подтверждение затягивается до `confirmDeadline` (32с) и часть
   источников остаётся inconclusive-show вместо авторитетного вердикта.

## 4. Одиссея vs контентные фильмы (конкретика из прошлой live-матрицы)

| фильм | primary | confirm (strict-сканы) | итог карточки | фаза B |
|---|---|---|---|---|
| **Одиссея 2026** (пустой) | все 6 балансеров 503 → inconclusive-show | строгий скан **всех** источников → HIDE | всё HIDE, cached 60с | плейбека нет → задержки не видно |
| **Матрица 1999** (контент) | zetflixdb/zagonka/xvc → 200 content (стоп рано) | строгий скан только пустых (kinoflix/hdvb-флап) | часть SHOW + часть HIDE | `/videos` + `/video` на кластере |
| **Интерстеллар 2014** (контент) | часть 200 content | строгий скан пустых | SHOW/HIDE | то же |
| **Паразиты 2019** (пустой) | 503 → inconclusive-show | строгий скан → HIDE (503-окно) / SHOW (accsdb-окно) | HIDE, cached 60с | плейбек почти не происходит |

Одиссея «работает нормально» не потому что карточка быстрее (у неё strict-сканов БОЛЬШЕ), а потому что
**там нечего запускать**. Разница в ощущаемой скорости — это разница «HIDE → ничего не запускаем» против
«SHOW → идём в кластер играть», а не разница в скорости availability.

---

## 5. Вердикт: MANIYA BUG / UPSTREAM

**Смешанный.**

- **UPSTREAM:** само время ответа кластера (503/медленные хосты, троттл на аккаунт, 15с таймаут
  `SkazClient.fetch`) — не наше.
- **MANIYA BUG (частично):** лишний полный скан перед плейбеком, который пин обязан был убрать, но не
  убирает — из-за (а) короткого 60с TTL пина, привязанного к `HIDE_TTL_MS` чужого источника, и
  (б) отсутствия перезаписи пина на cache-hit. Это прямое нарушение §4 спекы: «если источник SHOW, не
  должен выполняться лишний полный scan перед playback, если уже имеется валидное подтверждение».

Критерий §5 выполнен: одинаковый flow (карточка→видео), одинаковый тип контента, наша логика неправильно
использует cache/TTL и из-за этого повторяет дорогой скан.

---

## 6. Минимальный fix (концептуально, НЕ применён — READ-ONLY)

Одна строка + одна ветка:

1. **Отвязать TTL пина от hide-кэша.** В `availability.js` писать пин с независимым TTL
   (`ttlMs`/отдельная константа), а не `pinTtl = hasConfirmedHide ? HIDE_TTL_MS : ttlMs`. Пин описывает
   ГДЕ контент конкретного источника; скрытие другого источника не должно его укорачивать.
   Пин и так self-heal: любой не-FOUND рекомпут его чистит (`availability.js:1219-1223`), поэтому
   длинный TTL не «вешает» устаревший хост.

2. **Перезаписывать пин на cache-hit.** В `card()` перед `return` на hit — пробежаться по `hit.sources`
   и пере-установить FOUND-пины (те же условия `isFound`). Иначе кэшированная карточка оставляет `/videos`
   без пина, и польза от single-flight/cache теряется на плейбеке.

Оба изменения локальны в `availability.js`, не трогают `probe/confirm/providers/registry` и не меняют
семантику HIDE/SHOW — только устраняют повторный полный скан перед плейбеком.

Не предлагаю дополнительных аудитов. STOP.
