# BALANCER-KODIK-005 — отчёт: «Kodik есть при первом открытии, исчезает при повторном»

**Дата:** 2026-08-14 · **Режим:** READ-ONLY (код не менялся, ни commit, ни deploy)
**Вердикт:** Kodik исчезает **на слое 2 — в ответе `/api/lampa/sources/card`**. Причина —
не баг кэша и не баг UI, а **нестабильный вердикт кластерной пробы** `checksearch=true`
для балансера `kodik`: кластер в разные моменты отвечает на один и тот же запрос
по-разному (503 / 200-страница-похожих / accsdb), и код availability трактует эти
ответы как «показать» или «спрятать». Кэш карточки маскирует флип только в окно TTL
(60 с при любом скрытом источнике, 5 мин иначе); повторное открытие после TTL
пере-пробует кластер и берёт НОВОЕ состояние → kodik переключается.

---

## 1. Где именно исчезает Kodik (по слоям запроса)

| Слой | Участие | Вердикт |
|---|---|---|
| 1. `/api/lampa/sources` | Статический реестр, все `show:true`, kodik всегда на месте | **НЕ здесь.** Состав/порядок идентичны между открытиями (проверено, см. §4) |
| 2. `/api/lampa/sources/card` | Динамический per-card вердикт через кластер | **ЗДЕСЬ.** `show:true→false` появляется именно в этом ответе |
| 3. `applyCardAvailability` (UI) | Только применяет `row.show` к `sources[key]` | **НЕ баг.** Чистая аппликация без stale-merge; реестр — источник истины для списка |
| 4. UI-рендер | `component()` создаёт свежие `sources={}`/`filterSources=[]` на каждом открытии (Activity.push) | **НЕ баг.** Стейд не «помнит» первое открытие |

---

## 2. Механизм (root cause)

`/sources/card` для native-источника kodik делает `checkBalancer('kodik')` → проба
кластера `/lite/kodik?checksearch=true` (хост-ротация primary→online8). Вердикт —
функция состояния кластера **в момент пробы**. Для одного и того же фильма кластер
отвечает тремя разными способами, и каждый трактуется по-своему:

| Ответ кластера | Что это | Вердикт availability |
|---|---|---|
| **503** (пусто) на всех хостах | Сатурация/ошибка ноды, НЕ «контента нет» | **SHOW** `inconclusive:true authoritative:false` (оптимистично) |
| **200 + страница похожих фильмов** (только `method:link similar:true`) | Поиск не нашёл фильм; отдал «похожие» | **HIDE** `authoritative:true` (`verdict=absent`) + подтверждение |
| **200 + `{"accsdb":true,"msg":"Войдите в аккаунт…"}`** | Отказ авторизации учётки, НЕ «нет контента» | **SHOW** `inconclusive:true accsdb` |
| 200 + настоящая play/call-карточка | Фильм реально есть (в основном восточный каталог) | **SHOW** авторитетно |

Состояние кластера для одного запроса **меняется во времени**: одна и та же Матрица
в один прогон дала accsdb (trace-kodik-native-005, online8), в другой — 200-страницу
похожих (trace-kodik-005-root). Поллинг 6×8 с показал стабильность внутри минуты, но
между окнами (минуты) состояние разное.

Кэш (`fnv1aKey(id:serial:source:count:userUid)`) отдаёт сохранённый вердикт, пока не
истёк TTL:
- **TTL = 60 с** (`HIDE_TTL_MS`), если в записи есть хоть один `show:false` —
  включая сам kodik, когда он скрыт, и включая чужие скрытия (у Форреста скрыты
  `cdnvideohub!`, `skaz-kinopub!`). То есть **любой** hidden-источник укорачивает
  жизнь записи до 60 с.
- **TTL = 5 мин**, если все строки `show:true`.

Поэтому повторное открытие (позже 60 с, если что-то скрыто; позже 5 мин в любом
случае) — это cache MISS → повторная проба → новое состояние кластера. Флип
`show:true → show:false` происходит ровно тогда, когда первая проба попала в
503/accsdb-окно (ложный показ), а вторая — в здоровое 200-«нет»-окно (честное
скрытие).

### Ложность «показа» Kodik
Нативный Kodik-API (KodikClient search, `trace-kodik-native-005`) для Форреста,
Матрицы и Интерстеллара возвращает **found=false, 0 items** — западные тайтлы в
каталоге kodik-токена отсутствуют. Значит любой `kodik=show` у этих фильмов —
**ложный позитив** (кластер ошибся/отказал учётке → показали оптимистично). Пример:
у Форреста кластер стабильно 503 → kodik стабильно «показывается», хотя контента нет.

## 3. Сценарий пользователя

1. Открытие карточки → cache MISS → проба в 503/accsdb-окне → `kodik=show` (ложно).
2. Выход.
3. Повторное открытие через >60 с (запись жила 60 с — в ней был какой-то hidden,
   напр. `cdnvideohub`/`skaz-kinopub`, или сам kodik) → cache MISS → проба в
   200-«нет»-окне → `kodik=hide`. **«Kodik исчез».**

Обратное направление (показался после того как был скрыт) — тот же механизм:
переход 200→503/accsdb.

**Вторичный сценарий (не проверялся, требует уточнения по конкретному фильму):**
если два открытия приходят из разных точек входа (поиск vs «похожие» vs история),
у movie-объекта могут различаться поля (`id`/`kinopoisk_id`/`imdb_id`), → другой
cache key → свежая проба даже при быстром повторе. В жизненных тестах с одинаковыми
параметрами флипа при 3-секундном повторе НЕТ (второе открытие = cache HIT).

## 4. Доказательства

### 4.1 Прод-API, быстрый повтор (gap 3 с), 4 фильма — 0 флипов, второе открытие = HIT

```
Форрест Гамп  : kodik FIRST=true  SECOND=true   cached false→true
Матрица       : kodik FIRST=false SECOND=false  cached false→true
Интерстеллар  : kodik FIRST=false SECOND=false  cached false→true
Дом Дракона   : kodik FIRST=false SECOND=false  cached false→true
/sources состав и порядок идентичны FIRST↔SECOND (все 4).
```

Прод-состав 16 источников; у Форреста в ряду скрыты `cdnvideohub!`, `skaz-kinopub!`
→ TTL записи = 60 с (важно для §3).

### 4.2 Настоящий checker.card() (локальный импорт `createAvailabilityChecker`, креды VPS) — внутренние поля ряда kodik

```
Форрест  : show=true  status=503 host=online8  inconclusive=true authoritative=false
Матрица  : show=false status=200 host=online3  authoritative=true confirmed=true
Интерстеллар: show=false status=200 host=online3 authoritative=true confirmInconclusive=true
Дом Дракона: show=false status=200 host=online3 authoritative=true confirmed=true retried=true
Одиссея  : show=false status=200 host=online3  authoritative=true confirmed=true retried=true
```
(кэш работает детерминированно: SECOND cached=true, elapsed 0.)

### 4.3 Сырые ответы кластера `/lite/kodik?checksearch=true` (online3/online8)

- **Форрест:** 503 пусто на всех хостах (6/6 в поллинге) → вердикта нет → показ.
- **Матрица:** 200, страница из 36 `method:link similar:true` карточек —
  «Армитаж: Полиматрица», «Армитаж: Двойная матрица», «Коробка», «Брок: на пределе»…
  → предикат `checkSearchPredicate(body, query)` = `work=false verdict=absent rch=false`
  → скрытие.
- **Интерстеллар:** 200, «Интерстелла 5555», «Я злой лорд межгалактический»… → absent.
- **Дом Дракона:** 200, «Дракон в поисках дома», «Наш дом», «Дом совы», «Танец дракона»… → absent.
- **Одиссея 2026:** 200, «Бесконечная одиссея капитана…», «Черепашья одиссея»… → absent.
- (в другом окне, trace-kodik-native-005: Матрица/Интерстеллар/Форрест на online8 →
  `{"accsdb":true,"msg":"Войдите в аккаунт Настройки - Синхрони…"}` → показ.)

### 4.4 Сравнение с другими источниками (по требованию задачи)

| Источник | Поведение в прогонах | Причина стабильности |
|---|---|---|
| **Kodik** | Флапает show↔hide | 3 состояния кластера; TTL 60 с при любом hide |
| **Filmix** | Всегда show | `TRUSTED_ALWAYS_VISIBLE` — вообще без пробы (политика) |
| **Rezka** | Стабильно show (в этих прогонах; Одиссея hide) | Кластер отвечает предсказуемо |
| **skaz-kinopub** | Скрыт у Форреста/Интерстеллара | content-«нет» от primary (KINOPUB-004: Одиссея/Последний дом items=0) — стабильный сигнал |

## 5. Что НЕ является причиной

- Баг кэша (ключ/параметры одинаковые — вердикт одинаковый; SECOND — детерминированный HIT).
- Баг UI (`applyCardAvailability`/рендер/`sortMenuOpen`): слой применяет ответ как есть,
  стейд свежий на каждое открытие (BALANCER-UI-001 уже учтён и работает).
- Пропажа из статического реестра: kodik всегда в `/sources`.

## 6. Наблюдение для дальнейшего (код НЕ менялся)

Если нужно сделать kodik предсказуемым, есть два разных рецепта (реализация — отдельной
задачей, не в этой):

1. **Прижать ложные показы:** трактовать 503/accsdb от кластера для kodik как «вердикта
   нет» и НЕ показывать источник, для которого native-поиск даёт 0 items (гибрид
   native+cluster). Форрест/Матрица/Интерстеллар перестанут светиться ложно.
2. **Увеличить стабильность вердикта:** поднять `HIDE_TTL_MS` для confirmed-absent
   kodik, либо отдельный (более длинный) TTL для подтверждённых «нет».

Это только варианты на будущее — в рамках KODIK-005 код не тронут.
